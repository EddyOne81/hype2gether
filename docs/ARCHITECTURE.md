# Architecture

## Principles

- Monorepo, one language (TypeScript) end to end.
- Thin client, authoritative server, pure shared game logic.
- Every DB change is a migration; every table has RLS.
- Generated native folders (`ios/`, `android/`) are not committed (Expo Continuous Native Generation). Native config goes through `app.config.ts` and config plugins.

## Layout

```
hype2gether/
├─ apps/mobile/
│  ├─ app/                    Expo Router screens (thin)
│  └─ src/
│     ├─ features/            party, leaderboard, activity, checkin, card, auth, profile
│     ├─ services/            supabase client, health (HealthKit adapter), notifications
│     ├─ components/          shared UI
│     └─ config/env.ts        reads EXPO_PUBLIC_* only, validated with zod
├─ packages/scoring/          pure functions + Vitest; exports RULE_VERSION
├─ packages/shared/           types, zod schemas, constants
├─ supabase/
│  ├─ migrations/             schema + RLS + indexes
│  ├─ functions/              edge functions (Deno)
│  ├─ seed.sql                fake data only
│  └─ tests/                  RLS / SQL tests
├─ docs/  (PRODUCT_BRIEF, ARCHITECTURE, SECURITY, adr/)
└─ .github/workflows/ci.yml
```

Dependency direction: `apps/mobile` → `packages/*`; `supabase/functions` → `packages/scoring`, `packages/shared`. Packages never import apps.

## Domain modules

Code is organised by domain:
`auth`, `profile`, `party`, `round`, `steps`, `activity`, `checkin`, `scoring`, `card`, `notification`, `moderation`.

- App: `apps/mobile/src/features/<domain>/` → `api.ts` (Supabase calls only), `hooks.ts` (TanStack Query), `screens/`, `components/`. Screens never call Supabase directly.
- Server: one Edge Function per use case, named `<domain>-<action>` (e.g. `party-join`, `round-finalize`), each validating input with a zod schema from `packages/shared`.
- DB: one migration per change, prefixed by domain in its name.

## Contracts

- `packages/shared/src/db.types.ts` is generated by `supabase gen types typescript` and committed; CI regenerates and fails on diff.
- Edge Function request/response schemas live in `packages/shared/src/contracts/`; app and functions import the same schema.

## Access rules (RLS summary)

- A user reads a party's data only if they are a member.
- Clients may insert: their own step summaries, activities, check-ins, votes, reactions, reports.
- Members of a round can read the activities of the round's members that start inside the round.
- Clients may never write: daily_points, weekly_results, rating_history, cards, rounds.status.
- Storage: private `checkins` bucket, path `{party_id}/{round_id}/{user_id}/...`, read via signed URLs for members only.

## Key flows

1. **Step sync:** app opens → HealthKit daily aggregate per day in party time zone → upsert daily totals → server recomputes the day's points. No reliance on background sync; push reminders before the 12 h deadline.
2. **Activity sync:** app opens → HealthKit walking, running and cycling workouts since the last sync → upsert summaries (never the route) → server marks validity and recomputes the affected days' points.
3. **Check-in & vote:** camera capture → upload to private bucket → insert check-in → members vote (24 h window).
4. **Finalize round:** scheduled function runs after deadlines → loads facts → `packages/scoring` → writes results in one transaction → status final or provisional. Safe to re-run.
5. **Card:** client renders from stored results with Skia, captures 9:16/4:5 PNG, user previews and shares via share sheet. Activity cards read the route from HealthKit on the device at render time and trim it before drawing.

## Testing strategy

| Layer                | Tool                                                                                             | Runs where                                    |
| -------------------- | ------------------------------------------------------------------------------------------------ | --------------------------------------------- |
| Scoring engine       | Vitest, table-driven cases from PRODUCT_BRIEF                                                    | locally + CI                                  |
| RLS and SQL          | pgTAP (or SQL tests) against a throw-away local Supabase (`supabase start`)                      | CI (Docker available there); optional locally |
| Invariant check      | SQL test: no table in `public` without RLS + policy; no client write grant on server-only tables | CI                                            |
| Edge Functions       | Deno tests with mocked Supabase client                                                           | locally + CI                                  |
| App logic            | Jest/Vitest for hooks and pure UI logic                                                          | locally + CI                                  |
| End-to-end on device | manual checklist per feature code during pilot; automated mobile e2e later                       | physical iPhone                               |

CI uses its own isolated stack and never touches the hosted dev project or anyone's `.env`.

## Environments

- Supabase: `dev` and `prod` projects (separate keys). Never point a dev build at prod.
- EAS build profiles: `development` (dev client), `preview` (TestFlight internal), `production`.
- Config per environment via EAS environment variables; only `EXPO_PUBLIC_*` values reach the app bundle.
