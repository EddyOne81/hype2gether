# 0004 — Expo Continuous Native Generation (no committed native folders)

- Status: accepted
- Date: 2026-11-12

## Context

The app is React Native with Expo, iOS first, built in the cloud with EAS from Windows machines. It needs native capabilities (HealthKit, camera, Skia) that are not in Expo Go, so it runs as a development build.

## Decision

- Use Expo Continuous Native Generation: `ios/` and `android/` are generated by `expo prebuild` / EAS Build and are git-ignored.
- All native configuration lives in `apps/mobile/app.config.ts` and config plugins.
- Use a development build (`expo-dev-client`) instead of Expo Go; EAS build profiles `development`, `preview` and `production`.
- Expo Router for navigation, with screens in `apps/mobile/app/` kept thin.
- Dependency versions for Expo modules follow the SDK's bundled versions (`expo install`).

## Consequences

- No Xcode project to maintain or merge; SDK upgrades regenerate native code.
- A native module without a config plugin needs one (or a local plugin) before it can be used.
- Changes to native dependencies or app config require a new development build; JS-only changes do not.
- Builds require EAS (cloud), which suits Windows development; signing credentials are managed by EAS and never stored in the repo.
